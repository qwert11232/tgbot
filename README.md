# 🧭 AI Workspace Blueprint — инструкция для ИИ-агента

**Этот файл — точка входа. Прочитай его целиком, прежде чем что-либо делать в репозитории.**

Это **шаблон**, а не проект: прикладного кода здесь нет. Всё содержимое — два слоя:

1. **`.ai/` — слой управления ИИ.** Универсальный, переносимый, не привязанный к конкретному
   приложению: правила, память, брифы, рецепты.
2. **Код приложения** — то, что появится позже. Его структура заранее неизвестна: имена
   каталогов, стек и архитектура могут быть любыми.

Правило разделения: **`.ai/` описывает, как работать; код описывает, что работает.**
Не смешивай одно с другим и не переноси бизнес-логику в `.ai/`.

Пока проект не начат, единственное содержимое репозитория — `.ai/`, этот `README.md`
и `.gitignore`. Отсутствие кода — ожидаемое состояние, а не потеря файлов: **не ищи
и не восстанавливай приложение, которого здесь не должно быть.**

## 🚦 Шаг 0. Обязательный порядок действий (не пропускать)

Выполняй строго по порядку. Каждый шаг подтверждается фактом, а не намерением.

| # | Действие | Результат |
| --- | --- | --- |
| 1 | Прочитать этот `README.md` | понятна структура и правила слоя ИИ |
| 2 | Прочитать `.ai/MEMORY.md` | известно состояние проекта и прошлые решения |
| 3 | Прочитать `.ai/RULES.md` | известны законы кода, git и безопасности |
| 4 | Развернуть скиллы из `.ai/skills.txt` | методики доступны локально |
| 5 | Определить границы задачи (бриф) | понятно, что делаем и что не делаем |
| 6 | Работать по `RULES.md` | изменения соответствуют стандартам |
| 7 | Записать результат в `.ai/MEMORY.md` | преемник поймёт решение |

**Запрещено** начинать правки кода до выполнения шагов 1–5. Если файл `.ai/MEMORY.md`
пуст или содержит только шаблон — сначала заполни раздел `CURRENT PROJECT STATE`
фактическим состоянием (стек, точка входа, команды запуска и проверок), затем продолжай.

## 🗂️ Карта слоя управления

```text
.ai/
├── MEMORY.md              # память: критические правила, состояние проекта, лог решений
├── RULES.md               # манифест: стандарты кода, git, безопасность, Definition of Done
├── skills.txt             # каталог внешних скиллов (GITHUB_ID), разворачивается локально
├── PROMPTS/
│   ├── initial-brief.md   # бриф на новый проект с нуля
│   └── feature-request.md # бриф на отдельную фичу
├── DEPLOY/
│   └── db-bootstrap/      # как в проекте появляется db-setup.sql (шаблон + правила)
└── ASSETS/
    ├── screenshots/       # скриншоты: как есть сейчас, как должно быть
    └── mockups/           # макеты, схемы, чертежи
```

**Назначение файлов — коротко:**

- `MEMORY.md` — *состояние и аргументация*. Что работает, что сломано, почему принято решение.
  Живой документ, обновляется в каждом значимом изменении, ограничен по объёму.
- `RULES.md` — *законы*. Как писать код, что нельзя ломать, как логировать, когда задача
  считается выполненной. Меняется редко, действует всегда.
- `skills.txt` — *источники методик*. Список репозиториев с готовыми практиками;
  разворачивается в `.ai/skills/` (в git не попадает).
- `PROMPTS/*` — *постановка задачи*. Шаблоны брифов: цель, стек, логика, критерии приёмки.
- `ASSETS/*` — *визуальный контекст*. Скриншоты и макеты, на которые ссылаются брифы.
- `DEPLOY/db-bootstrap/` — *инфраструктурный рецепт*. Шаблон SQL, который поднимает схему
  на чистой managed-базе одной вставкой, и правила его получения. Сам `db-setup.sql`
  генерируется под схему **конкретного** проекта и живёт в его корне — в универсальный
  каркас он не входит.

## 🛠️ Шаг 4 подробно: разворачивание скиллов

`.ai/skills.txt` — текстовый каталог. Формат записи:

```text
GITHUB_ID: <owner>/<repo>
```

Строки с `#` — комментарии. Алгоритм:

1. Прочитать файл, собрать для каждой записи URL:
   `https://github.com/<owner>/<repo>.git`.
2. Склонировать **только для чтения**, без истории, в отдельную папку:
   ```bash
   mkdir -p .ai/skills
   git clone --depth 1 https://github.com/<owner>/<repo>.git .ai/skills/<owner>_<repo>
   ```
3. Прочитать в каждом репозитории `SKILL.md`, `skill.md` или `README.md` —
   именно там описана методика.
4. Применять методики **к коду проекта**, адаптируя под текущий стек. Копировать чужие
   файлы целиком в проект нельзя: это источник конфликтов и несовместимых зависимостей.
5. Папка `.ai/skills/` — локальная. Она в `.gitignore`, её содержимое не коммитится и
   не считается частью проекта.

Если `skills.txt` пуст или содержит только комментарии — работай без внешних скиллов
и не выдумывай ссылки. Если клонирование недоступно (нет сети/прав) — зафиксируй это
в `MEMORY.md` и продолжай по уже известным стандартам.

## 📜 Шаг 5 подробно: работа по правилам

Из `RULES.md` обязательны к исполнению всегда:

- **Чистый код**: минимально достаточное решение, явные имена, без мусора и «заготовок».
- **Не ломать существующее**: удаление или переписывание функций — только с записью
  аргументации в `MEMORY.md` (что, зачем, какие альтернативы, какие риски).
- **Беречь контекст**: точечное чтение файлов, никаких простыней логов в ответе,
  компактная память вместо «архива знаний».
- **Логировать**: значимые сценарии и ошибки — с уровнем и без секретов и персональных данных.
- **Безопасность**: секреты только в окружении, валидация на границе, проверка прав на сервере.
- **Git**: одна задача — одна ветка, осмысленные коммиты, без секретов и артефактов сборки.

Порядок работы над задачей:

1. Взять бриф (`.ai/PROMPTS/initial-brief.md` для нового проекта,
   `.ai/PROMPTS/feature-request.md` для фичи) или задачу от владельца.
2. Найти границы изменения: какие папки/файлы затрагиваются, что существует до тебя.
3. Реализовать минимальное решение, покрывающее критерии приёмки.
4. Проверить запуском: линт, типы, тесты, сборка — всё, что есть в проекте.
5. Обновить `.ai/MEMORY.md` и, при необходимости, документацию проекта.
6. Отчитаться владельцу: что сделано, чем проверено, что осталось, какие риски.

## 🧠 Шаг 7 подробно: ведение памяти

`MEMORY.md` — не дневник, а инструмент преемственности. Три обязательных раздела:

- **CRITICAL RULES** — короткий список того, что нельзя нарушать никогда.
- **CURRENT PROJECT STATE** — снимок «как есть сейчас»: стек, точка входа, команды,
  статус проверок, что работает, что сломано, что отложено.
- **ARGUMENTATION LOG** — журнал решений в формате: контекст → решение → альтернативы →
  риски → проверка. Новые записи сверху. Отвечает на «почему», а не «что».

Требования: файл держится в пределах ~200 строк; устаревшие записи сжимаются до одной
строки, а не удаляются; запись добавляется до того, как задача объявлена выполненной.

## ✅ Definition of Done (общий для любых задач)

- [ ] Критерии приёмки из брифа выполнены и проверены запуском.
- [ ] Линт / типы / тесты / сборка проходят — или явно объяснено, почему нет.
- [ ] Существующее поведение не сломано; несовместимости описаны с планом миграции.
- [ ] Секретов, отладочного кода и артефактов сборки в коммите нет.
- [ ] Запись в `ARGUMENTATION LOG` и обновлённый `CURRENT PROJECT STATE`.
- [ ] Отчёт владельцу: результат, проверки, остатки, риски.

**Не считается выполненным:** «написал, но не запускал», «должно работать»,
«тесты упали, но это не связано» (без доказательства связи).

## 🚫 Чего делать нельзя

- Начинать правки без чтения `README.md` → `MEMORY.md` → `RULES.md`.
- Удалять или переименовывать код, папки и файлы без аргументации в памяти.
- Менять секреты, ключи, CI, миграции и схему БД без явного разрешения владельца.
- Копировать содержимое `.ai/skills/` в проект и коммитить его.
- Коммитить секреты, дампы, `node_modules`, сборки, кэши.
- Расширять задачу «заодно»: побочные находки — в раздел `Backlog`.
- Заявлять о готовности без фактической проверки.

## 🔁 Передача смены (handoff)

Агент, завершающий работу, оставляет:

1. `CURRENT PROJECT STATE` — актуальный снимок (что работает / что сломано / что дальше).
2. Запись в `ARGUMENTATION LOG` со ссылкой на бриф и коммит.
3. Раздел `NEXT STEPS` — 1–3 конкретных следующих действия.

Агент, принимающий смену, начинает ровно с этого места: читает память, проверяет,
что описанное состояние совпадает с реальным (`git status`, запуск проверок), и только
потом продолжает. Расхождение памяти и реальности — отдельный дефект: сначала исправить
память, потом кодить.

## 🗄️ Схема БД на новом проекте: `db-setup.sql`

Универсальный каркас **не содержит** готового SQL: схема зависит от продукта. Вместо файла
в каркасе лежит рецепт — `.ai/DEPLOY/db-bootstrap/README.md` + `template.sql`.

Порядок для нового проекта:

1. Взять `template.sql` как скелет: `BEGIN; … DDL … обязательные данные … учёт миграций … COMMIT;`
   плюс блокировку проверок в конце.
2. Сгенерировать содержимое под свою схему: из миграций либо `pg_dump --schema-only`.
3. Заменить все плейсхолдеры `[ ... ]`: идентификаторы владельца, имена схем, версии.
4. Проверить на **чистой** базе, а не на рабочей.
5. Положить как `db-setup.sql` в корень проекта, упомянуть в `README.md` в разделе деплоя.
6. Записать в `.ai/MEMORY.md`, коммитится файл или генерируется по требованию.

Почему не в каркасе: файл, привязанный к одной предметной области (например, «товары —
заказы — платежи»), в другом проекте вреден: он выглядит как инструкция, но создаёт
чужие таблицы. Первичный источник правды о схеме — миграции, `db-setup.sql` — вторичный,
и он обязан обновляться в том же коммите, что и схема.

## 🧩 Как использовать этот каркас в новом репозитории

1. Скопировать **всё содержимое** репозитория (`.ai/`, `README.md`, `.gitignore`) в корень
   нового проекта — именно для этого он и создан. Ничего удалять не нужно.
2. Заполнить `CURRENT PROJECT STATE` в `.ai/MEMORY.md` фактами о проекте.
3. Заполнить в `.ai/RULES.md` плейсхолдеры `[ ... ]`: стек, линтер, тесты, язык, модель доступа.
   Заодно завести обязательные артефакты из `RULES.md` §4.1: `.env.example` и
   `db-setup.sql` по шаблону `.ai/DEPLOY/db-bootstrap/template.sql`.
4. При необходимости добавить скиллы в `.ai/skills.txt` и скриншоты в `.ai/ASSETS/`.
5. Первую задачу поставить через `.ai/PROMPTS/initial-brief.md` либо
   `.ai/PROMPTS/feature-request.md`.
6. Слой `.ai/` менять только по мере реальной необходимости — не «на всякий случай».

Соглашение об именах задач: бриф на проект — `PROMPTS/initial-brief.md`,
бриф на фичу — `PROMPTS/feature-<кратко>.md` (копия шаблона, чтобы рецепт остался в истории).
