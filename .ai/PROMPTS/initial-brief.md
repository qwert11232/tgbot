# 📝 Initial Brief — бриф на запуск нового проекта

> Заполняется владельцем за 5–10 минут. Агент читает этот файл первым, если проект
> начинается «с нуля». Пустые поля — не ошибка: агент задаёт вопросы по ним, но не
> придумывает ответы сам.
>
> Как использовать: скопируйте файл в `PROMPTS/brief-<дата>.md`, заполните, отдайте агенту.

---

## 1. Цель

**Что делаем (одна-две фразы):**
`[Например: сервис записи на консультации с оплатой и личным кабинетом]`

**Какую проблему решаем:**
`[Что болит у пользователя сейчас и почему текущее решение не устраивает]`

**Для кого:**
`[Основная аудитория, её контекст: телефон/десктоп, скорость интернета, язык]`

**Как поймём, что получилось (метрика успеха):**
`[Например: пользователь оформляет заказ за ≤ 3 минуты без обращения в поддержку]`

**Вне рамок (что точно НЕ делаем в этой версии):**
`[Например: нет мобильного приложения, нет мультиязычности, нет админ-панели]`

## 2. Стек и окружение

| Параметр | Значение |
| --- | --- |
| Язык / фреймворк | `[например: TypeScript + Next.js]` |
| База данных | `[например: PostgreSQL (managed), ORM]` |
| Хостинг / деплой | `[например: Vercel Hobby, ограничения: крон не чаще 1 раза в сутки]` |
| Аутентификация | `[например: вход через внешний сервис, роли в БД]` |
| Внешние интеграции | `[платежи, боты, почта, карты — с ограничениями и лимитами]` |
| Обязательные ограничения | `[бюджет, бесплатный тариф, регион, соответствие требованиям]` |

**Переменные окружения (имена, без значений):**
```
[KEY_1=]
[KEY_2=]
```
**Где лежат реальные секреты:** `[панель хостинга / менеджер секретов; в чат не отправлять]`

**Существующий код:** `[нет / есть, точка входа: путь; менять нельзя: список]`

---

## 3. Логика

**Основной пользовательский сценарий (по шагам):**
1. `[Пользователь открывает ... и видит ...]`
2. `[Выбирает ..., система проверяет ...]`
3. `[Оформляет ..., получает ...]`

**Данные (главные сущности и связи):**
```
[Entity A] 1—N [Entity B] — [что храним и зачем]
```

**Правила и краевые случаи:**
- `[Что происходит при ошибке сети / повторном нажатии / пустом списке]`
- `[Ограничения: остатки, лимиты, срок жизни заказа, таймауты]`
- `[Что нельзя потерять при сбое: деньги, заказы, загруженные файлы]`

**Права доступа:**
`[Кто что видит и может: гость / пользователь / менеджер / владелец]`

---

## 4. Критерии приёмки

Проверяемые утверждения — каждое можно подтвердить запуском или наблюдением.

- [ ] `[Сценарий 1 работает целиком от начала до конца]`
- [ ] `[Некорректный ввод даёт понятную ошибку, а не падение]`
- [ ] `[Данные сохраняются и переживают перезапуск]`
- [ ] `[Нет секретов в репозитории и в логах]`
- [ ] `[Проверки проекта зелёные: линт / типы / тесты / сборка]`
- [ ] `[Пустое состояние и состояние ошибки выглядят осмысленно]`

---

## 5. Ограничения по процессу

- Язык интерфейса и кода (комментарии/сообщения): `[русский / английский]`
- Стиль дизайна: `[сдержанный, тёплый / корпоративный; что точно не хотим]`
- Можно ли добавлять зависимости: `[да, минимально / нет]`
- Нужны ли миграции БД: `[да, с планом отката / пока нет]`
- Что делать при неоднозначности: `[спросить и ждать / выбрать минимальный вариант и записать в MEMORY]`
