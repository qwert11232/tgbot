# 🗄️ db-bootstrap — как в проекте появляется «SQL одним файлом»

> **Что это.** Раздел про один конкретный артефакт: файл `db-setup.sql` в корне проекта,
> который поднимает схему БД на чистой managed-базе (Neon, Supabase, RDS, любой веб-SQL-editor)
> одной вставкой. Здесь — универсальный шаблон и порядок его получения.
>
> **Чего здесь нет.** Готового SQL конкретного приложения: схема зависит от продукта,
> поэтому файл генерируется в каждом проекте заново. Пример для этого репозитория
> (магазин: товары, заказы, платежи) лежит в истории git — коммит `0092bc1`, файл
> `neon-setup.sql`; как референс структуры его можно посмотреть через
> `git show 0092bc1:neon-setup.sql`, но для другого проекта он не подходит.

---

## 1. Когда файл нужен

- Хостинг БД — managed-сервис с веб-консолью, а CLI миграций недоступен или не запускается
  (нет Node на машине, корпоративный прокси, чужой ноутбук).
- Нужно поднять окружение «с нуля» за один шаг: staging, демо, восстановление после удаления
  проекта в панели.
- Требуется передать состояние схемы человеку, который не будет запускать миграции.

**Когда не нужен:** если `migrate` работает в CI/локально — он и есть источник правды.
Дублировать схему в двух местах (миграции + SQL-снапшот) опаснее, чем не иметь снапшота:
файл устаревает молча.

---

## 2. Как получить файл для конкретного проекта

### Вариант А — из миграций (предпочтительно)

```bash
# 1) Сгенерировать миграцию из схемы (если её ещё нет)
[команда генерации миграций проекта]      # например: npx drizzle-kit generate --name init

# 2) Собрать один SQL из всех миграций
[команда сборки]                          # например: cat migrations/*.sql > db-setup.sql
```

Плюс: файл детерминирован и совпадает с миграциями. Минус: нужно знать порядок применения.

### Вариант Б — снапшот живой базы

```bash
pg_dump "$DATABASE_URL" --schema-only --no-owner --no-privileges > db-setup.sql
```

Плюс: гарантированно рабочее состояние. Минус: дамп содержит мусор (служебные схемы,
владельцев) — читайте перед коммитом.

### Вариант В — вручную по шаблону

Используйте `template.sql` из этой папки: он задаёт скелет (DDL → данные → учёт миграций →
проверка) и не содержит ничего проектного.

## 3. Обязательные требования к файлу

1. **Идемпотентность либо явное предупреждение.** Либо `IF NOT EXISTS`/`ON CONFLICT`,
   либо крупная шапка: «рассчитан на чистую базу, повторно не запускать».
2. **Одна транзакция** `BEGIN; … COMMIT;` — чтобы падение посередине не оставило полубазу.
3. **Плейсхолдеры вместо персональных данных.** Telegram ID, e-mail владельца, тестовые
   записи — только как `[ЗАМЕНИТЕ: …]` с комментарием, где взять значение.
4. **Учёт миграций.** Если в проекте есть таблица применённых миграций — вставьте запись,
   иначе первый же `migrate` попытается накатить всё заново.
5. **Блок проверки в конце** (закомментированный): сколько таблиц ожидается, есть ли владелец,
   какие индексы критичны.
6. **Никаких секретов и токенов** — только структура и служебные записи.
7. **Заголовок с датой и версией схемы** — чтобы через месяц было понятно, чему он соответствует.

## 4. Где файл живёт и коммитится ли

| Вопрос | Ответ |
| --- | --- |
| Имя | `db-setup.sql` в корне проекта (не `neon-setup.sql`: сервис может смениться) |
| Коммитить? | Да, если деплой ручной и файл — часть инструкции. Нет, если миграции автоматические и файл генерируется по требованию — тогда он в `.gitignore` |
| Обновление | При каждом изменении схемы — перегенерировать в том же коммите, иначе файл врёт |
| Где упомянуть | `README.md` проекта: раздел деплоя, «если миграции не запускаются» |

Решите это один раз при старте проекта и запишите решение в `.ai/MEMORY.md`
(раздел ARGUMENTATION LOG), чтобы преемник не создавал третий источник правды.

## 5. Чек-лист перед передачей файла человеку

- [ ] Файл проверен на **чистой** базе (новый проект/ветка), не только на рабочей.
- [ ] Повторный запуск не ломает базу (или это явно запрещено шапкой).
- [ ] Плейсхолдеры персонализированы, секретов нет.
- [ ] Учёт миграций синхронизирован с реальными миграциями.
- [ ] В конце — запросы проверки, ожидаемые числа указаны.
- [ ] В `README.md` проекта написано: когда применять и что делать, если таблицы уже есть.
